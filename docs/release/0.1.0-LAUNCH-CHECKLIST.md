## Go/No-Go Criteria

### Must Have — Blockers

- [ ] Every canonical P0 ledger entry is `Passed` against the exact distributed candidate; none is skipped, flaky, stale, waived, or supported only by a lower proof plane.
- [ ] `M1_COMPLETE_GREEN` through `M4_COMPLETE_GREEN` exist for the clean exact candidate and all first-class acceptance criteria pass.
- [ ] The exact signed/notarized app, DMG, and update archive pass identity, entitlement, Gatekeeper, clean-machine, recovery, offline, update, and signature-preservation checks.
- [ ] Runtime capabilities equal the release manifest, website, README, privacy notice, terms, support documents, and release notes.
- [ ] Privacy and terms are adopted, the private disclosure channel is verified, and component/model/license obligations are closed.
- [ ] Rollback and incident rehearsals pass without replacing immutable versioned bytes.
- [ ] The repository operator explicitly approves publication of the exact immutable candidate.
- [ ] After publication, the repository operator separately approves the exact website deployment and canonical readback completes.

### Should Have

- [ ] Two recurring operators complete two real meetings each without data loss or false state.
- [ ] Product walkthrough and contributor architecture guide are complete.
- [ ] One independent contributor completes setup and the candidate gate from a clean clone.

### Nice to Have

- [ ] Application-specific selection in addition to validated all-system audio.
- [ ] More local model choices than the first qualified engine/model pair.
- [ ] More export renderers than the canonical evidence package and basic text formats.

## Rollback Plan

### Trigger Conditions

- A data-loss, false-Recording, privacy-scope, credential, signing, update, capability-overclaim, or canonical-byte mismatch is discovered.
- A P0 receipt becomes invalid, stale, irreproducible, or bound to different bytes.
- Notarization, Gatekeeper, clean-machine launch, update, offline operation, or canonical readback fails.

### Rollback Steps

1. Freeze signing, publication, appcast advancement, and website deployment authority.
2. Before publication, delete only candidate outputs and preserve failure receipts.
3. After GitHub publication but before canonical deployment, mark the immutable release withdrawn or prerelease and do not advertise it.
4. After canonical deployment, restore the preceding content-addressed website pointer and remove the bad release from the current appcast without replacing its bytes.
5. Publish an application repair only under a higher version after the complete gate reruns.
6. Notify users through verified security/support channels with content-free remediation instructions.

### Rollback Owner

Release owner, with the repository operator retaining final authority.

### Rollback Time Objective

Freeze protected publication within 15 minutes of a confirmed P0 incident; restore the prior canonical website/appcast pointer within 60 minutes when an admitted prior release exists.
